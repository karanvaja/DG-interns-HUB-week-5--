## Q4: How to Read an Email Header

### Email headers are the metadata of an email. They record the path the message took, the servers involved, authentication results, and addresses used for routing and replies. Reading them correctly is a core Tier 1/Tier 2 skill for phishing triage. Below is an explanation of the key fields, followed by a summary table.

## Key Header Fields Explained

### 1. Received Chain
* Every mail server that handles the message prepends a Received: header.

* The chain is read bottom-to-top: the bottom-most Received: is the originating server (closest to the sender); the top-most is the last hop (your mail gateway).

* Each entry typically shows: from (server name/IP), by (receiving server), with (protocol, e.g., ESMTP/ESMTPS), and a timestamp.

* Use the chain to identify the true originating IP, detect relays, and spot timing anomalies.

* Look for gaps or mismatches — e.g., a "from" name that doesn't resolve to the stated IP, or a long chain suggesting spoofing/relaying.

* Example:
Received: from mx.company.com (mx.company.com [203.0.113.10])
        by mail.company.com with ESMTPS id abc123
        for <user@company.com>; Mon, 17 Nov 2025 10:22:31 +0000
Received: from unknown (unknown [198.51.100.77])
        by mx.company.com with SMTP id xyz789
        for <user@company.com>; Mon, 17 Nov 2025 10:22:28 +0000

→ Bottom line shows the originating IP 198.51.100.77 (from an "unknown" host — a red flag).


## 2. Return-Path
* The envelope sender — where bounces (NDRs) are sent.

* Usually equals the MAIL FROM used in SMTP and is what SPF checks.

* Can differ from the visible From: (legitimate for ESPs/newsletters, suspicious otherwise).

## 3. Reply-To
* The address that will receive the reply when the user hits Reply.

* Legitimate when a company sends from no-reply@ but wants replies to go to support@.

* Suspicious when Reply-To points to a different domain than From: — a common BEC/phishing trick.

## 4. Message-ID
* A unique identifier for the message, generated by the sending mail system.

* Format: <unique-string@domain> — the domain part should match the sending organization's domain.

* Used for threading and tracking; also useful to search logs and correlate with other reports.

* Mismatch between the Message-ID domain and the From:/Return-Path domain is a red flag.

## 5. Authentication-Results
* Added by the receiving mail server (your gateway) and records the outcome of SPF, DKIM, and DMARC checks.

* Format: Authentication-Results: mx.google.com; spf=...; dkim=...; dmarc=...

* dmarc=fail with spf=pass/dkim=pass for a different domain = spoofing (no alignment).

* Always trust the top-most (receiving) Authentication-Results over any injected by the sender.

## Summary Table

| **Header Field** | **Purpose** | **Red Flag Indicator** |
|---|---|---|
| **Received** | Records each server hop; read bottom-to-top to trace the true origin | Originating IP is unknown/blacklisted; "from" hostname doesn't match its IP; long or inconsistent chain; timestamps out of order; message delayed unusually long |
| **Return-Path** | Envelope sender; where bounces go; used by SPF | Domain differs from `From:`; free-mail domain (gmail/yahoo) for a corporate sender; empty `<>` on a non-bounce message |
| **Reply-To** | Address that receives replies | Different domain from `From:`; free-mail address; lookalike domain (e.g., `examp1e.com`) |
| **Message-ID** | Unique message identifier; used for threading/correlation | Domain in Message-ID doesn't match sender's domain; malformed or missing Message-ID; random/odd format |
| **Authentication-Results** | Records SPF/DKIM/DMARC outcomes from the receiving server | `dmarc=fail`; `spf=fail`/`softfail`; `dkim=fail`; passes belong to a different domain than `From:` (no alignment); `none` when a policy is expected |


## Practical Triage Workflow
* Open the full raw header (not the rendered email).

* Read Authentication-Results first — quickest signal of spoofing.

* Read the Received chain bottom-to-top — find the originating IP; check its reputation.

* Compare From:, Return-Path, and Reply-To — mismatches are suspicious.

* Check Message-ID domain — should match the sender organization.

* Extract IOCs (IPs, domains, Message-ID) and pivot to threat intel / SIEM.

## Key Takeaways
* Bottom of Received chain = true origin; top = your gateway.

* From: is trivially spoofable — never trust it alone; cross-check with Return-Path, Reply-To, and DMARC.

* dmarc=fail is the strongest single indicator of a spoofed sender.

* Reply-To mismatch is a hallmark of BEC.

* Message-ID domain mismatch is a subtle but useful corroborating signal.
